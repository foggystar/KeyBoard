1. 先只记四个 BLE 词

术语在你的项目里作用
Peripheral（外设）STM32WB55 键盘板广播并等待连接
Central（中心设备）手机扫描并发起连接
Advertising（广播）P2PSRV1连接前告诉周围设备“我在这里”
GATTP2P 服务和特征连接后规定数据放在哪里、怎样读写或通知

今天只做到“广播”；连接和 GATT 写入放到下一阶段。Bluetooth SIG 的官方 Primer 将 advertising 描述为连接前的无连接通信，并将可被手机连接的设备称为 Peripheral。阅读官方 BLE Primer

2. STM32WB55 里有两个 CPU

你的 main.c
    │
    ▼
CPU1 / Cortex-M4                    CPU2 / Cortex-M0+
运行你的应用       ── IPCC ──▶      运行 ST BLE Stack
                                      │
                                      ▼
                                  2.4 GHz RF ──▶ 手机

CPU1 负责你的键盘逻辑和 BLE 应用；CPU2 负责实时性很强的 Link Layer、GAP/GATT 和射频交互。两者通过共享内存传数据、通过 IPCC 发通知。ST 的 AN5289 给出了这套双核分工。

两份固件：VS Code 平时烧录的是 CPU1 应用；CPU2 的 BLE Wireless Stack 是另一份固件。第一个断点就是用来确认 CPU2 固件是否已经存在。

3. 沿着 main() 走一遍

① MX_APPE_Config()
读取芯片 OTP 中的 HSE 调谐值。它必须早于系统时钟配置。
↓
② SystemClock_Config()
启动 32 MHz HSE 和 PLL，建立 CPU1 的 64 MHz 系统时钟。
↓
③ IPCC / RTC / RNG / RF Init
分别准备双核通知、软件定时、随机数和射频子系统。
↓
④ MX_APPE_Init()
初始化共享邮箱并等待 CPU2 发出 ready 事件；ready 后才进入 BLE 初始化。
↓
⑤ APP_BLE_Init()
启动 CPU2 BLE Stack，初始化 GAP、GATT 和 P2P 服务，然后请求广播。
↓
⑥ MX_APPE_Process()
反复运行事件调度器。它必须持续执行，所以 LED 不能再用两次 500 ms 的阻塞延时。

CFG_LPM_SUPPORTED=0 表示首次测试保持运行，不进入会关闭 HSE 的深度低功耗；CFG_USE_SMPS=0 表示不启用你尚未补齐电感网络的 SMPS。它们首先是安全的 bring-up 选择，不是最终键盘的功耗方案。

5. 第一次实机练习：只看两个返回值

  1. 用 VS Code 编译并通过 ST-LINK 烧录当前 wb55test。
  2. 在 app_ble.c 的 SHCI_C2_BLE_Init() 后打断点。
  3. 运行并单步越过调用，查看 status：目标是 SHCI_Success（通常为 0）。
  4. 继续运行，在 aci_gap_set_discoverable() 后停下，查看 ret：目标是 BLE_STATUS_SUCCESS（通常为 0）。
  5. 继续运行，不要停在断点；手机扫描 P2PSRV1。
停在哪里你已经证明下一嫌疑
第一个调用前CPU1 时钟和初始化至少走到 BLE继续看 CPU2 返回值
SHCI_SuccessCPU2 Stack 存在，IPCC 通信基本正常GAP/GATT 和广播请求
BLE_STATUS_SUCCESS协议栈接受了广播配置HSE 实际频偏、RF 匹配和天线
手机看到名称广播数据真的经过射频到达手机下一课测试连接与 GATT
