第 4 课 · 真实故障 · 约 10 分钟

为什么 RTC 有时钟却无法初始化

目标：看懂调用栈、HAL 返回值和 RTC 的两层写保护，并能解释为什么缺一行代码会让 INITF 永远不置位。

1. 调用栈告诉了我们什么

main()
  └─ MX_RTC_Init()
       └─ HAL_RTC_Init()
            └─ RTC_EnterInitMode() → HAL_ERROR
                 └─ Error_Handler()

这条调用栈证明错误发生在 BLE 初始化之前。Error_Handler() 只是统一的“错误停车场”；真正根因是 RTC_EnterInitMode() 返回失败。

3. 备份域是什么

备份域是芯片中特意独立出来的一小块区域，包括 RTC、备份寄存器以及相关时钟控制。它的目的，是让普通系统复位甚至主电源变化时，时间和少量关键数据仍有机会保留。

正因为它要“保留”，STM32 对它加了额外保护。ST 的 RM0434 参考手册规定：系统复位后，备份域默认禁止写入；必须把 PWR_CR1.DBP 置 1 才能写。

4. 两把锁，而不是一把锁

外层锁：DBP保护整个备份域。调用 HAL_PWR_EnableBkUpAccess() 打开。
内层锁：RTC_WPR保护 RTC 配置寄存器。HAL 通过写入特定解锁序列打开。

HAL_RTC_Init() 已经执行了 __HAL_RTC_WRITEPROTECTION_DISABLE()，它只打开内层锁。如果外层的 DBP 仍是 0，软件还是不能修改 RTC。

5. 本次故障是怎样形成的

① 系统复位
备份域写权限恢复为禁止，但 RTC 时钟选择可能继续保留为 HSE/32。
↓
② CubeMX 生成代码检查 RTCSEL
发现当前已经是 HSE/32，于是不需要切换时钟源。
↓
③ 缺少无条件解锁
HAL_RTC_MspInit() 没有主动调用 HAL_PWR_EnableBkUpAccess()，所以 DBP=0。
↓
④ INIT 写入无效
软件请求进入初始化模式，但备份域仍禁止写。
↓
⑤ INITF 永不返回
硬件没有收到有效请求，HAL 等待超时并返回 HAL_ERROR。

6. 为什么这一行能修复

/* USER CODE BEGIN RTC_MspInit 0 */
HAL_PWR_EnableBkUpAccess();   // PWR_CR1.DBP = 1
/* USER CODE END RTC_MspInit 0 */

调用后，外层写保护被解除。随后 HAL 再解开 RTC_WPR 内层保护，设置 INIT=1；RTC 硬件确认后设置 INITF=1，初始化继续执行。ST 对相同的 STM32WB 超时现象也给出了这一修复。查看 ST 技术答复
